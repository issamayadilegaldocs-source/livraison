# Livreur site

On 2026-11-17, the repo pivoted from the full Hamma platform to one small Next.js app, `livreur-site/`. The legacy platform is in git history before branch `feat/livreur-site`.

**Product.** Each independent rider ("livreur") buys a copy of a site that works like hamma-delivery.com. The copy pre-fills every restaurant of the rider's city from a dump. Customers confirm on the site; the server emails the order to the rider, and the customer then sends the pre-written order to the rider on WhatsApp (free, official). The business model is one dump per city and one copy per rider.

The original design documents (v1 order flow, v2 catalogue) are in git history under `docs/superpowers/specs/`.

## Sales and maintenance model (decided 2026-11-20)

Goal: maintaining N sites must stay simple.

- **One Cloudflare account per rider.** Each has its own Pages project and its own R2 bucket named `livreur-bons` (the name is fixed in `wrangler.toml`; create it in each account). Riders' data is isolated by account. Images are uploaded to each rider's own bucket.
- **The rider owns his strategy.** Promos, coupons, commission, delivery fees, free delivery, hours: he sets them himself on his config page (`/api/config?cle=<CONFIG_CLE>`). Saved in R2 as `config/<whatsapp>.json`, live in under 2 minutes, no redeploy. `clients/<client>/livreur.json` holds only the starting values (the saved config overrides them). So the owner never maintains rider strategy.
- **`whatsapp` must be unique across `clients/`.** Locally all clients share one fake R2, keyed by number: two clients with the same number would share promos. `scripts/preparer.mjs` refuses to build in that case (test in `scripts/scripts.test.ts`).
- **Adding restaurants** (shared by all sites of a city): `npm run import` → `npm run images` → then `npm run deploy-tous`. Images must reach every rider's bucket, and every site must be redeployed.
- **Updating all sites at once:** `npm run deploy-tous [-- <client> ...] [--sans-images]` reads `secrets/clients.json` (repo root, git-ignored via `/secrets/`): per client `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `MEDIA_BASE_URL_PROD`. It uploads missing images, then deploys; one failing client does not stop the others. Use a Cloudflare token limited to Pages + R2 of that account, and keep an encrypted backup of the file (Cloudflare cannot show a secret again). `scripts/deploy-tous.mjs` has no unit test; only the placeholder refusal was run by hand.

## How it works

- **Hosting: static site on Cloudflare Pages (since 2026-11-18).** Next builds with `output: 'export'` into `out/`, and `npm run deploy -- <client>` uploads it with `wrangler pages deploy`. Every rider has one Pages project (project name = client folder) and one subdomain. Only `functions/` runs code, all under `/api/` so one rate-limiting rule covers it: `POST /api/commande`, `POST` + `GET /api/bon/<id>`, `GET /api/etat`, `/api/config` and `POST /api/colis`. Their logic lives in `lib/serveur.ts`, which has no `fs` and no Node APIs, so vitest tests it with an in-memory R2 or mocked Supabase. Static pages never invoke a Function, so they stay free and unlimited. There is no middleware. The previous Docker/VM deployment (`Dockerfile`, `deploy/`) no longer matches the code and will be removed once Cloudflare is live.
- **Backend storage adapter (`lib/supabase.ts`, added 2026-11-22).** All runtime persistence (`livreur_configs`, `commandes`, `coupon_usages`, `push_subscriptions`, and receipt PNGs in `bons`) goes through the `Stockage` interface in `lib/supabase.ts` (`stockage(env)`). When `SUPABASE_URL` (or `NEXT_PUBLIC_SUPABASE_URL`) and `SUPABASE_SECRET_KEY` (or legacy `SUPABASE_SERVICE_ROLE_KEY`) are set, the backend talks directly to Supabase PostgREST (`/rest/v1/*`) and Storage (`/storage/v1/object/bons/*`) via Web Standards `fetch` (zero extra npm dependencies, stays within the 10 ms Worker CPU budget); otherwise it falls back to the Cloudflare R2 binding `BONS`. Schema lives in `supabase/schema.sql` with RLS enabled and zero `anon`/`authenticated` access — only server-side Functions with the secret key can read/write operational tables (protecting customer PII and rider pricing from the public publishable key). New `sb_secret_…` opaque keys are sent on the `apikey` header only (never `Authorization: Bearer`).
- **One rider per build.** `clients/<client>/livreur.json` holds the name, colour, WhatsApp, email, city and delivery fee, validated by zod (`lib/livreur.ts`). `scripts/preparer.mjs` (run by `npm run dev` and `npm run build`) copies the chosen client's file to `.build/livreur.json`. The client is `CLIENT`, or the only folder in `clients/`. The build reads that file, and `functions/api/commande.ts` imports it, so the rider's email ships inside the Function code and is never published as an asset. The city data is `villes/<dossierVille(ville)>/`, so riders of one city share it.
- **Catalogue = generated JSON.** `npm run import -- <dump> <ville>` runs `lib/import-dump.mjs` (plain `.mjs`, so it runs with bare node) and writes into `villes/<ville>/`:
  - `restos.json`: the discovery index, including dish names for search;
  - `menus/<id>.json`;
  - `cuisines.json`.

  `lib/catalogue.ts` reads them with `fs` at build time only. The data is committed (about 9 MB for Sfax: 298 restos, 20,736 dishes). Each page carries only what it needs:
  - The home page embeds the restos without dish names (about 260 KB instead of 740 KB).
  - The dish names load from `/recherche.json` on the first search.
  - Each `/resto/<slug>` page is pre-rendered with its own menu.
  - `/commande-data/<slug>` (resto + menu + media base, `app/commande-data/[slug]/route.ts`) is the small file the order Function reads through `env.ASSETS`. Parsing the whole `restos.json` there would risk the free plan's 10 ms CPU limit.
- **Images.** All copies share one public R2 bucket. The keys are flat, `<type>/{thumb,full}/<name>.webp`: dump names are `YYYY-MM-DD-<uniqid>`, assumed unique across cities (only Sfax has been checked), and flat keys match the existing bucket. The upload's size check is the safety net for that assumption; it assumes a fresh bucket or one filled by the same script. URLs are `MEDIA_BASE_URL` + key (`lib/media.ts`), fixed at build time. `npm run deploy` forces an https base (`MEDIA_BASE_URL_PROD`, default `https://livreur.hamma-delivery.com/media`: on 2026-11-18 `media.hamma-delivery.com` returned 404 for most images, a deploy with that default broke the images). `npm run images -- <ville> <dump-images>` writes webp into `media/`, outside `public/`: 1.2 GB / 36k files would break the Pages limit of 20,000 files per site, and `deploy` aborts if `out/media` exists. `npm run envoyer-images` lists the bucket (S3 API, `aws4fetch`) and uploads only the missing keys. An existing key with a different size stops the run instead of overwriting another city's image.
- **Menu out of the HTML.** `/menu-data/<slug>` (`app/menu-data/[slug]/route.ts`, `force-static`) holds `{categories, plats}` with client prices (markup applied at build, resto prices and rules never exposed). The resto page only renders the header; `MenuVivant` (`Vivant.tsx`) fetches the JSON after hydration and shows a skeleton / error message meanwhile. Why: passing the menu as a client-component prop wrote it twice (`.html` + `.txt` RSC), ~600 KB per page, 63 MB / 974 files for a city, and `wrangler pages deploy` was very slow. Now ~33 MB / 1273 files. Lesson: never pass big data as props to a client component in a static export; put it in a static JSON.
- **Deploy size/speed.** `generateBuildId` is fixed (`next.config.ts`): the default id sits in every HTML and changes each build, so Wrangler re-uploaded everything. `scripts/deploy.mjs` also deletes the RSC `.txt` next to each `.html` (only `next/link` fetches them; we use plain `<a>`). Do not reintroduce `next/link` without reverting that.
- **Hours.** `lib/horaires.ts` computes hours in `Africa/Tunis`, where `day` 0 is Sunday. A resto with no schedules counts as open ("Horaires non communiqués"). The HTML is built once, so open/closed is computed in the browser (`useMaintenant` in `lib/maintenant.ts`, refreshed every minute; `Discovery`, `app/resto/[slug]/Vivant.tsx`). Before hydration everything shows as open with no label, so nothing false is displayed. The order Function re-checks with the server clock and refuses closed restaurants.
- **Options.** `lib/options.ts`:
  - a `single` group gives min 1 / max 1 when required ;
  - a `multi` group gives min `max(1, min)` when required, and max `max` (or the number of options when it is 0) ;
  - prices are computed in millimes.
- **Delivery fee.** `lib/livraison.ts` computes the fee as `base + parKm × (haversine × facteurRoute)`, rounded up to 0.5 DT and clamped to `[min, max]`. It refuses addresses beyond `rayonMaxKm` (road km). The settings live in `livreur.json` under `livraison` (owner choice on 2026-11-18: 1 DT + 0.5 DT/km, min 1 so the formula applies from the first km, max 12, 15 km, factor 1.3; no routing API). Restaurant coordinates come from the dump (`position`, present for 303/303). The customer position comes from the browser Geolocation API; there is no map pin yet. Later the map pin was added (`ChoixAdresse`). *Lesson (2026-11-21):* a wrong point reached the rider because a ≥150 m network fix (or the resto position when GPS is unavailable) was the map's start centre and "Valider" sent it untouched. Now the map opened without a chosen position (`ajuster`) keeps "Valider" disabled until the customer drags the map, picks a search result, or sits on a ≤150 m GPS dot. `position.precision` (m, only for a direct GPS fix) travels to the server and the rider's email says "GPS du téléphone, ± X m" or "point choisi sur la carte" (`originePosition`).
- **Orders.** `POST /api/commande` takes `{restoSlug, lignes: [{platId, qte, choix: {groupIndex: optionIndex[]}}], client, position: {lat, lng}}`. It validates with zod and checks the slug against `^[a-z0-9-]{1,120}$` before any file read. It recomputes everything from `/commande-data/<slug>`, never from client prices, and refuses closed restaurants, invalid options and addresses out of range. The rider's message includes Google Maps links to the customer and to the restaurant.
- **Delivery to the rider.** The Function emails the order (HTML + text, with the ticket link) to `livreur.email` (plus the Telegram / push alerts below). The cart no longer has a "send on WhatsApp" step (removed 2026-11-21 on the owner's request): after `/api/commande` succeeds the customer goes straight to « Commande envoyée ». The response still carries `texteWhatsApp` / `numeroWhatsApp` (unused by the cart now; `lienEnvoiWhatsApp` still serves the parcel form). An email failure does not block the order.
- **History: why the customer used to send it on WhatsApp.** Decided on 2026-11-18, reversed 2026-11-21: no free and reliable server-side WhatsApp exists (Meta Cloud API is paid, CallMeBot is closed to new sign-ups, WAHA needs a server, and the site is static on Cloudflare). Telegram was dropped. The email is the automatic safety net.
- **Customer email (optional).** `client.email` in the order body (validated by `CommandeInputSchema`, remembered in `localStorage` with the other contact fields). If present, `traiterCommande` sends a second Resend email to the customer (`htmlClientCommande` / `texteClientCommande` in `lib/email-html.ts`): items, delivery, and « Montant à payer » (client prices only: no resto price, margin or gain). Same fire-and-forget rule: a failure never blocks the order. The email is not kept in the order record (`fiche`).
- **Order email.** The Resend email is HTML (`lib/email-html.ts`: table layout, inline styles, dish thumbnails from the absolute media base) with a plain-text fallback. It has no attachment any more: it links to the ticket.
- **Optional automatic WhatsApp.** `lib/whatsapp.ts` can also send the text through CallMeBot when `CALLMEBOT_APIKEY` is set (unofficial, text only; it answers HTTP 200 even on errors, so the body is checked).
- **Ticket (bon de commande), drawn in the browser.** Owner choice on 2026-11-18 (option B). The old satori + sharp rendering needed Node, a disk and far more than 10 ms of CPU. The flow:
  1. `/api/commande` returns `bon = {id: REF-<32 hex>, sig: HMAC-SHA256(BON_SECRET, id), donnees}`. `donnees` (`donneesBon` in `lib/bon.ts`) holds no customer data. The WhatsApp text and the email already contain `<origin>/api/bon/<id>`.
  2. The cart draws the PNG with the Canvas API (`lib/bon-canvas.ts`, no library, page font). It posts the PNG to `/api/bon/<id>?sig=…` and waits for it (5 s max) before showing the WhatsApp step: once the customer switches to WhatsApp, the phone may suspend the page and kill the upload.
  3. The Function checks the signature, the PNG magic bytes and the size (≤ 1.5 MB). It writes `bons/<id>.png` to the private R2 bucket `livreur-bons` (binding `BONS`, shared by all riders) only if the key is absent, so a signed id cannot overwrite a ticket.
  4. `GET /api/bon/<id>` serves the file. A bucket lifecycle rule deletes `bons/` after 7 days.

  Without `BON_SECRET` or `BONS`, there is no ticket and no link, and the order still goes out. The dish thumbnails need CORS on the image bucket; without it the canvas would be tainted, so they fall back to an icon. Browsers without `CanvasRenderingContext2D.roundRect` (iOS before 16) produce no ticket; the order still goes through. Trade-off: the customer's browser draws the ticket, so a determined customer could alter it; the email and WhatsApp text, computed by the server, remain the reference.
- **Rider settings page (pause, hours, fees, dish prices).** Owner request on 2026-11-18: the rider has no Cloudflare access and must handle day-to-day changes alone.
  - *Storage.* `config/<whatsapp>.json` in the `BONS` bucket (`lib/config.ts`, zod `ConfigSchema`); the WhatsApp number separates riders sharing the bucket. Fields: `pause`, `retour` (Tunis local date-time; `pauseEnCours` ends the pause by itself at that time); `service` (absent = `livreur.json`, `null` = no hours, object = these hours); `frais` (base, parKm, min, max, rayonMaxKm; `facteurRoute` stays owner-only); `plats[restoSlug][platId] = {prix?, indispo?}`. A corrupt object is ignored, so the site falls back to `livreur.json`. `reglages()` merges config over `livreur.json`.
  - *Page.* `/api/config?cle=<CONFIG_CLE>[&resto=<slug>]` (`pageConfig`, plain HTML, no JS except a dish filter). A wrong or missing key returns 404; the key is compared in constant time (SHA-256 digests). POST forms are urlencoded and validated (`appliquerFormulaire`); success answers 303, an error answers 400 with a message. The resto list comes from the static `/restos.json`, dishes from `/commande-data/<slug>`. A price equal to the menu price is not stored.
  - *Authoritative check.* `traiterCommande` loads the config first: pause and hours refuse the order; fees replace `livreur.livraison`; `prixClients` turns raw resto prices (or the rider's new resto price) into client prices with the markup, and drops unavailable dishes, before `calculerCommande`.
  - *Display.* Pages read `GET /api/etat[?resto=<slug>]` (`useReglages`, `lib/reglages.ts`, cached 2 min per resto in `sessionStorage`): the home page for its pause/hours banner, `MenuVivant` for pause, hours, fees and that resto's corrections. When the rider is stopped, `MenuVivant` sets `ouvert=false` and passes `messageFerme`, so the existing closed-state UI (banner, disabled checkout, no quick add) does the rest. Corrected dishes show the build price until `/api/etat` answers (a brief flash). Corrections are deliberately not baked into the build: a baked "unavailable" could not be undone without a redeploy.
  - *Pause display.* `BandeauLivreur` (in the layout, all pages) shows a large red banner with the announced return (`arret`, `quand`: « aujourd'hui / demain / vendredi 20 novembre à 14:30 »), or « Livraison fermée · reprise à 11:00 » outside hours. The home page greys out every resto card ("Livreur en pause"); the menu's own red block is hidden in that case, since the banner says it.
  - *Markup (owner, `livreur.json` → `majoration`).* Rules `{montant}` (DT added to the dish price, supplements unchanged) or `{pourcent}` (dish + supplements, `majorer`, rounded up to 100 millimes), for `tous`, per resto slug or per dish id; dish > resto > tous (`regleDuPlat`). `prixClients` applies them and keeps the resto price in `prixResto` (dish and options).
    - Raw resto prices stay in `villes/` and `/commande-data` (public, like the restaurant's own menu). The markup rules never leave the Function bundle and the build.
    - Resto pages get client prices only, computed at build, with `prixResto` stripped. A rider correction `prix` **is the client price** (the rider types what the customer pays; the resto price stays the menu's, so the email's « à payer au resto » is the original price and the gain = delivery + client price − resto price). A fixed price replaces the markup rule for that dish. `/api/etat` returns the corrections as they are. Lesson: it used to be the resto price + markup, and a rider who typed his selling price got a resto price of 12 DT and no margin in the email.
    - A rider's correction is a new *resto* price; the markup is added on top.
    - `calculerCommande` also computes `sousTotalResto`. The email shows resto price and margin per line plus « dont à payer au resto / dont votre majoration » (`marge`). The ticket for the restaurant uses resto prices. The WhatsApp text (sent by the customer) shows client prices only.
  - The footer no longer quotes the minimum fee, since the rider can change it.
- **Home by shop type (2026-11-18, design canvas « Accueil par catégories + Colis »).** The home page (`app/page.tsx`) is built to fit one phone screen without scrolling: search (submits to `/c/tout?q=`), Restaurants card, Colis card, then a 3-column grid of shop types. Illustrations are hand-made inline SVG components (`app/components/Illustrations.tsx`, generated from the canvas; gradient ids prefixed per component).
  - *Shop types* (`lib/types-commerce.ts`): keyword rules on the dump's names and categories, computed at build. A shop can have several types. Whether it is a *shop* (not in Restaurants) is decided on the name only, so a restaurant with a « Sels & épices » category stays a restaurant and is also listed under Épicerie. Sfax: 276 restaurants, 20 épicerie, 28 pâtisserie, 18 cafés, 2 fleurs, 12 parapharmacie, 1 animaux.
  - *Category pages* `/c/<type>` (`app/c/[type]/page.tsx`, static, one per type plus `tout`) reuse `Discovery` with a `titre`; cuisines chips only for restaurants. `Discovery` reads `?q=` from the URL on mount (static export: no server search params). Layout: sticky header (title, open count, search with clear button, 44 px chips); search results are a `RestoRow` list showing the matching dish ("Plat : …") when the resto name doesn't match. Rider settings page (`htmlConfig`) is one HTML document with three views switched by the URL hash in the browser (`#accueil` dashboard: service + summary tiles; `#prix`: resto list with search/filters/badges, then one resto's dishes via `&resto=<slug>`; `#reglages`: hours + fees) and a fixed bottom nav; without JS all sections show. "Prix des restos" section: per dish it shows the initial menu price (struck through when changed), the rider's new resto price, and the client price (markup applied live in the browser with the same rounding as `majorer`, rule from `data-pct`/`data-mt` set by `regleDuPlat`); per-dish reset, Modified/Indispo filters, a "change all prices by N %" helper that only fills the fields (nothing saved until Enregistrer), and per-resto counters in the resto list. Saving is unchanged (`action=plats`, a price equal to the menu price is not stored). It shares the same look: Plus Jakarta Sans, `#f6f7fb` background, white 22 px cards, pill status chip, grey filled inputs.
- **Rider settings page redesign (2026-11-18, from the Design mockup).** Three tabs (Accueil / Prix / Réglages), phone-first. Accueil: big open/paused card, then three link cards (Prix des restos with counters, Horaires, Frais). Prix: resto list (search, Tous/Modifiés), then one resto: one card per dish with the **resto price as an editable field prefilled with the current resto price** (initial price struck once changed, « Client paie X » live with the markup, « Remettre », « Plus dispo ? » toggle), fixed bottom bar « Enregistrer N changements », the % helper folded in a `<details>`. Server rule unchanged: a price equal to the menu price is not stored. Réglages: horaires + frais in one form, `action=reglages` (= `horaires` then `frais`, all or nothing).
- **Simple price flow (« Changer le prix d'un plat »).** For low-literacy riders: home card → `?cle=…&simple=1#simple`, three steps on one view (`data-vue="simple"`): pick the resto, pick the dish (search, current price shown), then ONE big field « Nouveau prix chez le resto » + « Enregistrer le prix » (`action=prix1`, resto + plat + prix; `appliquerFormulaire`). Same storage as the full price screen (`plats[resto][platId].prix`; a price equal to the menu price removes the correction, `indispo` is kept); success redirects to `…&simple=1&resto=…#simple`. The full screen « Tous les prix et plats indisponibles » stays for availability and the % helper.
- **Restaurant filters = what you eat.** `/c/restaurants` chips come from `lib/filtres-plats.ts` (Sandwich, Pizza, Makloub, Mlewi, Tacos, Burger, Pâtes…), matched on the resto's `categories` (accent-insensitive substring), and only filters with at least one resto are shown. The old country cuisines (Maghrébine, Italienne, Turque…) are no longer used as chips (the data stays and is still searchable).
- **Service fee (`lib/frais-service.ts`).** Zigzag-style fee on top of delivery, kept by the rider: `clamp(pourcent % × client basket, min, max)`, millime-rounded (`calculerFraisService`). Zigzag preset (from 1,000 real orders, `food-delivery-multivendor` `zigzag-pricing-parity.md` §3): 8 %, min 0.8, max 5 (`FRAIS_SERVICE_ZIGZAG`, the « Mettre par défaut » button). Default is **no fee** (absent in `livreur.json` and config); `livreur.json` `fraisService` is the starting value, the rider's config page (`fraisService` in R2: absent = json, `null` = none, object = values) overrides it, shown by `/api/etat` for the browser preview. Base = the basket the customer sees (dishes incl. markup, no delivery), not the resto subtotal like Hamma: the browser only knows client prices, and the preview must match the server. The customer sees a separate « Frais de service » line (cart, WhatsApp text, email); the email's *gain* = delivery + markup + service fee (`gain`), *à payer au resto* is unchanged. `CommandeCalculee.fraisService` is included in `total`.
- **Tip (`pourboire`).** The customer picks 0 / 1 / 2 / 3 / 5 DT in the recap step; it is sent in the order body (`0–50`, optional), added to `total`, shown as its own line (cart, WhatsApp, email) and counted in the rider's *gain*. Not part of the resto amount or the service-fee base.
- **Rider alert on Telegram (`lib/telegram.ts`).** Email and WhatsApp are easy to miss, so the order Function also posts a short message (amounts, client, tap-to-open buttons) to the rider's Telegram chat through a bot (`TELEGRAM_BOT_TOKEN` secret + `telegram.chatId` in `livreur.json`). Free, loud notification, one `fetch` from the existing Function, so the site stays static. Optional `telegram.appel` (`@pseudo` or `+216…`) also triggers a free Telegram voice call through CallMeBot (the rider authorizes `@CallMeBot_txtbot` once); unofficial service, no SLA, the message is the reliable channel. Not a GSM call: that needs a paid telephony provider. Failures never block the order.
- **Config page simplified (2026-11-21).** Bottom nav is Commandes / Accueil / Réglages (the Prix tab is gone: prices are changed from the « Changer le prix d'un plat » tile on Accueil, and per-resto prices, unavailable dishes and closing live under Réglages › Restos). Accueil holds only on/off switches and that price tile, no settings list. Réglages is one flat list per topic. Commission is its own screen (`data-vue=commission`: resto list → one % field); the dish price screen has no commission field.
- **Distinct home-screen icons (2026-11-21).** The rider saves several pages to his phone's home screen; each has its own icon and short name so they are told apart: config « Réglages » (purple sliders, `public/icone-reglages.png`), `/api/push` « Alertes » (orange bell, `icone-alertes.png`, also in its manifest), `/api/commandes` « Commandes » (green clipboard, `icone-commandes.png`); the customer site keeps its own per-rider icon (`app/icon.tsx`). 512 px PNGs drawn from lucide paths with `sharp` (one-off, not a build step). iOS keeps an icon already saved: the rider must remove the old shortcut and add it again.
- **Order history (2026-11-21, `lib/historique.ts`, `functions/api/commandes.ts`).** Every order and parcel is saved as one JSON file `commandes/<whatsapp>/<id>.json` in `BONS` (one file per order: no read-modify-write on a shared file, so two simultaneous orders cannot overwrite each other). The `id` is `<9999999999999 − timestamp ms, 13 digits>-<ref>`: R2 lists keys alphabetically, so the newest orders come first with a plain `list`. The list is the first tab « Commandes » of the rider's config app (`/api/config?cle=…#commandes`, bottom nav; the home screen shows a « N en cours » card; `vueCommandes` in `lib/historique.ts`, all CSS scoped under `.cmd`), with sub-tabs « En cours » / « Historique »; `/api/commandes?cle=…` serves the same screen alone and receives the POSTs. The rider and taps « Livrée » or « Annuler »: a POST `{id, statut}` rewrites the file (`nouvelle` ⇄ `livree`/`annulee`, `fin` = date), same origin lock as the other POSTs. The list refreshes itself (no manual reload): the service worker posts `{type:'commande'}` to every open page when a push arrives, and the page also refetches itself when the app becomes visible again and every 30 s while visible, swapping only the `.cmd` block (open/closed cards kept). The push notification click now opens `/api/config?cle=…#commandes` (`public/sw-livreur.js`; phones pick up the new worker on their next visit). The save runs before email/push and never blocks the order (R2 error only logged). Files expire after **90 days** through an R2 lifecycle rule on prefix `commandes/` (set once per bucket, see README); the page reads only the **40 newest** files (free-plan limit of 50 subrequests per Function call; add pagination if a rider needs more). Each file also stores the body of the order email (`html`, from `htmlCommande`/`htmlColis`), so the page shows the same details as the email (amount to collect, due to the restaurant, rider gain, articles with photos, customer, map links) inside a collapsible card, with the date written out in Tunis time (« lundi 16 novembre 2026 à 12:00 »); the email's inline styles make it render as is, without an iframe. Fiches hold the customer's name, phone and address: that is why they are not kept forever.
- **Rider push alert (2026-11-20, `lib/push.ts`, `functions/api/push.ts`, `public/sw-livreur.js`).** The Telegram call goes through CallMeBot (unofficial, needs a one-time authorisation), and no web page can ring a phone, so the order Function also sends a Web Push to the rider's phones. The rider opens `/api/push?cle=<CONFIG_CLE>` once, taps « Activer », and the page subscribes (service worker `/sw-livreur.js?cle=…`, the key in its URL lets a notification click reopen `/api/config?cle=…`). Subscriptions are endpoint URLs in `BONS` (`push/<whatsapp>.json`, max 5, dead ones removed on 404/410); only known push hosts are accepted (`endpointValide`), so the Function never calls an arbitrary URL. Auth is VAPID (ES256 JWT with WebCrypto, private key = secret `VAPID_JWK`, public key derived from it). **The push has no payload** (no RFC 8291 encryption): the service worker shows a generic « Nouvelle commande » with `requireInteraction` and vibration; add aes128gcm encryption if the notification must show the amount. Sent for orders and parcels, never blocks them (errors only logged). The POST of `/api/push` has the same origin lock as the other POSTs. Not a phone call; not tested on iPhone; the service worker has no `fetch` handler so customer pages are untouched.
- **Commission and promos (`lib/commission.ts`, formulas from Hamma `earnings-split.ts` / `discount-funding.ts`).** Both are rider settings (`livreur.json` start values, rider config page overrides, stored as `commission` / `promos` in R2).
  - *Commission.* A % of the **resto price** per line (`commissionMil`), taken from the resto's share and kept by the rider; one level only: a % per resto (`pourcentCommission`; empty = none). No « all restos », menu or dish level (rider found it too complicated; old such values in a saved config are ignored). Commission (rider's cut of the resto price) and markup/`majoration` (added to the client price, `livreur.json`) are two separate settings and never share a screen. The customer sees nothing.
  - *Promo.* Automatic, one per order: the best of the active ones that match the resto and the minimum basket (`meilleurePromo`). `pourcent` (with optional max) or `montant`, always on the client basket and ≤ it. Funded by the rider (`livreur`), the resto (`resto`) or both (`partage`, resto pays `partResto` %, rider pays the rest: `repartirRemise`, the resto part is capped at what the resto still gets so the two parts always sum to the discount). `/api/etat` sends the browser `vueClient(promo)` only: never who pays.
  - *Money identity (tested).* `total = sousTotal − remise + livraison + frais de service + pourboire` and `total = dueResto + gain`, with `dueResto = prix resto − commission − part resto de la promo` and `gain = livraison + majoration + frais de service + pourboire + commission − part livreur de la promo` (can go negative if the rider funds a big promo). The service fee base is the basket after the promo. The ticket image for the resto still shows the plain resto prices (not net of commission/promo).
- **Small rider rules (`lib/regles-livreur.ts`, config page only, stored in R2).**
  - *Closed resto* (`restosFermes`, big button on the resto page): refused by `traiterCommande` (« indisponible »), greyed « Indisponible » on the home list (`Discovery`), closed state on the menu (`MenuVivant`).
  - *Minimum order* (`commandeMin`): checked on plats before promo (`calculerCommande` error with the missing amount); the cart disables « Passer la commande » and says how much is missing.
  - *Delivery supplement* (`supplement`: a manual « Pluie / Rush » switch with name + amount, and an automatic night window with amount): `supplementEnCours` uses Tunis time (UTC+1) on both server and browser. Paid by the customer on its own line, goes to the rider (`gain`), and is waived when delivery is free. The strip announces it while active.
  - *Announcement* (`annonce`, ≤ 140 chars): shown in `BandePromo` on every page.
  - *Tip amounts* (`pourboires`, 1–6 values, default 1/2/3/5): the cart buttons; the server still accepts any tip 0–50.
- **Parcel pricing, separate from meals (`ColisConfSchema`, `tarifColis` in `lib/colis.ts`).** A parcel is not a meal, so it has its own rule: own delivery price (start + per km, min/max, max distance), a size supplement (medium, large; small is never charged extra) and an on/off switch (`actif`: off = requests refused, form shows why). `reglages()` returns the resolved `colis: TarifColis` (distance fees + supplements; `facteurRoute` stays the rider's); without a rule parcels cost like a meal delivery with no supplement (old behaviour). Promos, coupons, service fee, tip and free delivery never apply to parcels. The form (`FormColis`) previews with the live rule from `/api/etat`, the Function recomputes. Config screen « Tarif des colis » with a reset button back to meal fees. The email shows `distance X + taille Y`.
- **Promotions and coupons are two separate things in the UI** (riders mixed them up when they shared one form). Same data (`Promo`; a `code` makes it a coupon), but two screens, two creation actions and two lists: « 🏷️ Promotions » (`promo-ajouter`: automatic, never has a code: any code sent is ignored, so an automatic promo can never silently become a hidden coupon) and « 🎟️ Coupons » (`coupon-ajouter`: the code is required; cumulable and usage limit live here). Each screen's explanation points to the other. Home has two cards, the dish page has two cards, and the pause/hide logic (public vs hidden) is unchanged. A coupon has a single field, its code, which doubles as its name: the customer reads « Coupon CODE » in the cart, WhatsApp text and email (`promo.libelle`: « Coupon CODE » or « Promo « nom » », joined by « + » when cumulated); the browser labels the coupon line with the code the customer typed.
- **Coupons.** A promo with a `code` (3–20 letters/digits, stored upper-case, unique per rider) is a coupon: it is never published (not in `/api/etat`, not in the build-time pages, not in the strip or badges), so nobody can read the codes. The cart has a « Code promo » field: `POST /api/coupon {code, resto}` (`verifierCoupon`) answers with the client view of that promo only (no funding, no code echo), the browser adds it to its preview. The order body carries the `code`; the server re-checks it in `calculerCommande`: a valid code beats the automatic promos, an unknown code or one that does not fit the order (resto, dish, minimum basket) rejects the order with a clear message instead of silently charging more. Funding (rider / resto / both) works like any promo. No usage limit yet (no per-customer store): a code works as long as the rider keeps it active, so stop or delete it to end it.
- **The resto price can be corrected too (`Correction.resto`).** The imported menu goes stale when a resto changes a price, so each dish has two rider prices: `resto` (what the resto now asks; what the rider pays it) and `prix` (what the customer pays). Without `prix`, the customer pays the new resto price + the markup rule; with `prix`, that fixed price wins. The corrected resto price feeds `prixResto`, so « somme due au restaurant », the gain, the commission base and the resto ticket all follow. `/api/etat` still sends the browser client prices only (`correctionsClient` turns a `resto` correction into resto + markup; the resto price itself is never published). A value equal to the menu or an empty field removes the correction. Edited on the dish page (« 🏪 Le resto vous le vend à » + « 💰 Le client paie », live margin); the dish rows show « (corrigé) ».
- **Parcel supplements beyond size.** `urgent` (added when the customer picks no time = « dès que possible ») and `nuit` (automatic window, tested on the chosen pickup time, or on the current Tunis time when none is chosen), both part of `supplementColis`; `supplements: {taille, urgent, nuit}` on the parcel and detailed in the email. The form preview uses the same function.
- **Coupon extras.** `cumulable` (coupon only): `promosAppliquees` applies the coupon **and** the best automatic promo (the 2nd discount never exceeds what is left of the basket); each discount keeps its own funding and the resto part stays capped at what the resto still gets; the email/cart show one line per promo, the totals are the sums. `limite` (coupon only): one tiny R2 object per order that used the code (`usages/<whatsapp>/<CODE>/<REF>`, listed to count: no counter to rewrite under concurrency; two simultaneous orders can overshoot by one, noted in the code). Checked in `verifierCoupon` and at order time, recorded when the order leaves; the promo list shows « Utilisé x fois sur N ».
- **Resto ticket is net.** The bon image keeps the resto prices on the lines, then lists what is taken off (rider commission, promo part paid by the resto) and ends with « À payer au restaurant » (`deductions`, `aPayer` in `donneesBon`; plain « Montant des plats » when there is nothing to deduct).
- **Free delivery (`lib/livraison-gratuite.ts`).** Rider setting `livraisonGratuite` (`livreur.json` start value; config page: absent = json, `null` = paid, `{}` = free for all, `{min}` = free from that basket). When it applies (`livraisonOfferte`, basket before promo ≥ min: a promo never costs the customer the free delivery) the customer pays 0 delivery: `frais` is 0 and `fraisOffert` keeps the real price for the texts; the rider bears it (his gain simply has no delivery part, so `total = dueResto + gain` still holds). The browser preview mirrors it (struck-through price + « Offerte »). `BandePromo` (in the layout, under the pause banner) shows « 🛵 Livraison gratuite dès 30 DT » and the general promo (no resto, no dish) on every page, from `/api/etat`, build-time `livreur.json` until then. Config screen « Livraison gratuite » has one big button to turn it on and one to stop it.
- **Promo on one dish.** A promo can carry `plat` (needs `resto`): the discount, the cap and the minimum apply to that dish's lines only (`meilleurePromo(…, parPlatMil)`, computed from the order lines on the server and from the cart in the browser; the dish must be in the cart). The rider creates it from the dish page (Prix → resto → plat → « Mettre ce plat en promo »). Customers see the badge on that dish only; the resto badge says « Plats en promo » when it has only dish promos (`etiquettePromo`, `etiquettePlat`).
- **Promos shown to customers.** `etiquettePromo` (resto promo before a general one, % before DT) gives the badge text (« −10 % dès 15 DT »). Home / category pages (`Discovery`): pink badge on cards, a « Promos » filter chip (only when a promo exists), a « 🏷️ En promo » section first, and promo restos ranked right after open ones. Resto page (`Menu`): a banner and a badge on every dish (the promo applies to the basket, so every dish of that resto gets it; the real discount is computed in the cart). Promos come from `/api/etat` (`reglages.promos`), build-time `livreur.json` ones until it answers.
- **Rider config page UX (made for non-technical riders).** One screen per setting (`data-vue`: horaires, frais, frais-service, commission, promos, plus accueil / prix / simple / reglages), chosen by the URL anchor (`VUES`, `ANCRE_APRES` for where a save returns). Each screen has its own colour (`--c` / `--t`), a hero header with an emoji, a yellow « À quoi ça sert ? » box in plain words, a hint under every input (`champ2`), and a live example box that recomputes while typing (small inline script: delivery price at 1/3/6 km, service fee on 5/15/40/80 DT, commission on 10 DT, promo on a 20 DT basket with who pays what). The promo form is 4 numbered steps with « who pays » as three big radio cards. Home and the Réglages tab share one list of coloured cards with a ✅ / ⚪ status line (`cartesReglages`). Keep new settings in this pattern. The price screens follow it too: « Prix et restos » (hero + explanation + numbered steps), the resto page (plain explanation, step 1 = dish prices, step 2 = close / commission cards, each dish row reads « 🏪 Resto · 💰 Marge · 📊 commission »), and the 3-step « Changer le prix d'un plat » (hero, explanation, big « Le client paie » field with a live result line). ## Lessons

- **Dump layout.** Restaurant covers live in `images/restaurant/cover/`, not `images/restaurant/`.
- **Image errors.** An SSR `<img>` that fails before hydration never fires React's `onError`. `Img` checks `complete && naturalWidth === 0` on mount.
- **Git Bash path rewriting.** Git Bash rewrites `VAR=/media` into a Windows path. Set it in `.env.local` instead.
- **Image size.** Images take about 1.2 GB after webp for Sfax (36,534 files, thumb + full). 79 source files are corrupt and fall back to the initial.
- **Two partial image hosts.** Dump image names can end with a bare dot (`2024-03-04-65e60d6f170b3.`, no extension): the key is `<name>.webp` (regex `/\.[^.]*$/` in `lib/media.ts` and `scripts/images.mjs`; with `[^.]+` it became `..webp`, a 404 everywhere). Neither `media.hamma-delivery.com` nor `livreur.hamma-delivery.com/media` has every image (checked 2026-11-18: ~1 % missing on the second, most recent covers missing on the first), so `<Img>` retries once on the other host (`urlSecours` in `lib/media.ts`) before showing the initial. Remove it once `npm run envoyer-images` has filled one bucket (needs `R2_*` keys in `.env.local`).
- **Existing bucket is incomplete.** On 2026-11-18, `media.hamma-delivery.com` lacked recent covers (e.g. `restaurant/full/2026-08-24-6a8c406707bad.webp` gave 404) and had no CORS. Run `npm run envoyer-images` on the new bucket before going live.
- **Static export.** Route handlers become files at build time (`force-static` + `generateStaticParams`), so `/recherche.json` and `/commande-data/<slug>` are plain assets. `.env.local` is loaded by `next build` too, so a dev `MEDIA_BASE_URL=/media` would leak into production: `npm run deploy` overrides it.
- **Raw `.txt` page (2026-11-20).** With `next/link` on a static export, a click downloads `/<page>.txt` (RSC data); when that fetch fails (weak network, redeploy with a tab left open) the browser navigates to the `.txt` and shows raw text. All internal links now use `app/components/Lien.tsx` (a plain `<a>`): real page loads, no `.txt` fetch. Do not import `next/link` again. The `.txt` files stay in `out/` (public, same data as the page; checked: no email, secret or markup rule inside).
- **Stale `wrangler pages dev`.** Starting it in the background from Git Bash leaves node + workerd processes alive after the shell exits. A second start can then serve the old instance with old `.dev.vars` (a new secret missing → 404). Kill every `wrangler pages dev` node process and `workerd` before restarting.
- **Git Bash and node paths.** `/tmp/x` in Git Bash and in node.exe are different folders; use real Windows paths for files shared between them.
